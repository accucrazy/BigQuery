Pandora × BigQuery · 工程實踐分享

為什麼 Pandora 選擇 BigQuery
一個社群聲量 AI 系統的真實使用心得

Text-to-SQL · 向量搜尋 · RRF Hybrid Search · Serverless 資料底座

跟著 Google 一起學 BigQuery，對我們來說最大的收穫，不只是學會一個資料倉儲工具，而是更清楚看見一件事：

AI 時代真正的競爭力，會發生在資料處理能力。

模型可以越來越強，介面可以越做越漂亮，但如果底層資料是亂的、慢的、不可查的，AI 最後只會變成一個講話很順的客服機器人。它看不到市場脈絡，也沒有辦法真正幫品牌做決策。

Pandora 是什麼

社群聲量 AI 系統，讓品牌用自然語言查市場脈絡

Pandora 是一個社群聲量 AI 系統，使用者可以直接用自然語言提問：

🔍
「幫我分析全家福袋近 14 天的負面討論。」
💊
「最近猛健樂副作用的討論集中在哪些平台？」
📊
「競品被抱怨最多的是價格、服務，還是產品效果？」

這些問題看起來像一般的聊天，但系統背後其實要同時完成三件很重的工作：

1

對上千萬筆社群長文做全文搜尋。

2

對 1536 維 embedding 做語意相似度搜尋。

3

把關鍵字結果與向量結果用 RRF 融合排名，找出真正相關的文章。

這也是我們最後選擇 BigQuery 的原因。

資料特性

Pandora 面對的資料，不是一般資料庫想像中的資料

我們處理的是社群上的真實語言：Dcard 文、Threads 貼文、PTT 推文、Facebook 留言、Mobile01 討論。這些資料有幾個很麻煩的特性：

很長

單篇平均約 2000 token，等於每一列資料本身都很重。

很多

資料量來到上千萬筆，每次查詢要在數百 GB 純文字裡快速找訊號。

難預測

LLM 動態生成 SQL，沒有人可以提前知道它會查什麼欄位、組出什麼條件。

不只關鍵字

「價格太盤」、「感覺被當韭菜」，背後都是「價格信任感不足」。

所以 Pandora 需要的不是一個單純存資料的地方，而是可以同時支援長文全文搜尋、ad-hoc SQL、向量搜尋、語意理解、聚合分析、戰情室監測、AI Agent 查詢的資料底座。這個工作負載，剛好打中 BigQuery 的甜蜜點。

工程實作

Pandora 在 BigQuery 上實際做的三件事

第一件事：Text-to-SQL，讓 LLM 直接查社群長文

當使用者輸入自然語言問題，Pandora 的 LLM Agent 會先理解問題，抽出品牌、產品、時間、情緒與平台條件，再動態生成 SQL：

BigQuery SQL · Text-to-SQL 示例
SELECT
  postId,
  title,
  SUBSTR(fContent, 0, 500) AS content,
  source, forumName, author,
  10 + IFNULL(counts_like, 0) * 3
      + IFNULL(counts_comment, 0) * 5 AS volume,
  pageCreatedAt, sentiment, url
FROM `pandora_analytics.datalake_picked`
WHERE (
  CONTAINS_SUBSTR(LOWER(title),     LOWER('全家')) OR
  CONTAINS_SUBSTR(LOWER(fContent),  LOWER('全家')) OR
  CONTAINS_SUBSTR(LOWER(forumName), LOWER('全家')) OR
  CONTAINS_SUBSTR(LOWER(tags_str),  LOWER('全家'))
)
AND SAFE_CAST(pageCreatedAt AS TIMESTAMP)
    >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 14 DAY)
ORDER BY volume DESC
LIMIT 200

這段 SQL 是 LLM 動態生成的——我們無法預測下一個使用者會問什麼，也不可能為每一種問題提前設計索引。BigQuery 的 Dremel 架構與 Capacitor columnar storage 讓查詢 fContent 時系統可以聚焦讀取需要的欄位，不需要把整列資料都拉出來。對上千萬筆長文資料，這個差異不只是快一點，而是整個查詢方式都變得可行。

第二件事：BigQuery 原生 VECTOR_SEARCH，處理語意相似度搜尋

關鍵字搜尋只能解決「有沒有提到這個字」。以「猛健樂副作用」為例，使用者可能寫的是：

打完之後有點噁心 食慾下降很明顯 胃不舒服嗎 Mounjaro 的反應

這些內容不一定包含完全相同的字，但語意上非常接近。Pandora 把文章轉成 1536 維 embedding，直接用 BigQuery 的 VECTOR_SEARCH 完成語意相似度查詢：

BigQuery SQL · VECTOR_SEARCH
WITH query_embedding AS (
  SELECT [/* 1536-dim float array */] AS embedding
),
vector_results AS (
  SELECT base.document_id, distance
  FROM VECTOR_SEARCH(
    (
      SELECT document_id, embedding
      FROM picked_embeddings
      WHERE ARRAY_LENGTH(embedding) = 1536
    ),
    'embedding',
    TABLE query_embedding,
    top_k => 200,
    distance_type => 'COSINE'
  )
)
SELECT
  vr.document_id AS postId,
  1 - vr.distance AS vectorScore,
  dp.title,
  SUBSTR(dp.fContent, 0, 500) AS content,
  dp.source, dp.forumName, dp.author
FROM vector_results vr
JOIN `pandora_analytics.datalake_picked` dp
  ON dp.postId = vr.document_id
ORDER BY vectorScore DESC

最重要的地方不是語法短，而是向量結果可以直接 JOIN 回主表。向量資料、文章 metadata、平台、情緒、聲量、時間都在同一個 BigQuery dataset 裡，不需要在多個資料庫之間搬資料、同步資料、比對 ID、補救延遲。

第三件事：RRF Hybrid Search，把關鍵字與語意結果融合

Pandora 會同時跑兩條路：關鍵字搜尋找出明確提到品牌的文章、向量搜尋找出語意上接近的文章，然後用 Reciprocal Rank Fusion 融合：

RRF 公式
RRF_score = 1 / (k + keywordRank) + 1 / (k + vectorRank)

RRF 的好處是它只看排名，不在意兩邊分數尺度不同。如果一篇文章在關鍵字搜尋裡排名第 5、在向量搜尋裡排名第 3，最終分數會自然提高。兩邊都覺得相關的文章，排到最前面。

TypeScript · Parallel BigQuery Queries
await Promise.all([
  vectorSearchPosts(queryEmbedding),
  keywordSearchPostsWithRank(keywords)
]);
// 兩路結果回來後，在 application layer 做 RRF rank merge

兩條查詢都送進同一個 BigQuery，回來後只需要在 application layer 做輕量 merge。架構簡單很多。

選型評估

為什麼不用 PostgreSQL？

PostgreSQL 是很好的資料庫。如果 Pandora 做的是會員系統、訂單系統、交易系統，PostgreSQL 很適合。但 Pandora 的核心工作負載完全不同：

⚠️長文全表掃描很痛苦

PostgreSQL 是 row-store。千萬筆 × 長文的工作負載，每次掃描 fContent 都會造成極大 I/O 壓力。就算加 GIN 或 pg_trgm 索引，索引本身也會巨大，寫入也會被放大。更麻煩的是查詢是 LLM 動態生成的，不可能提前為每一種變形建立 functional index。

🔧pgvector 和全文搜尋是兩個世界

用 PostgreSQL 做 hybrid search 大概需要：GIN / pg_trgm 做關鍵字搜尋、pgvector + HNSW 做向量搜尋、application layer 做 RRF、可能再加 Redis 快取。每個元件都能做事，但系統複雜度變高。你要維護全文索引、向量索引、HNSW 參數、vacuum、connection pool……對小團隊來說都是真實成本。

BigQuery 的價值在於，它把這些事情壓回同一個資料平台。我們不用為了做一個 AI 輿情系統，先養出一個資料庫維運團隊。

核心優勢

BigQuery 對 Pandora 最關鍵的幾個優勢

☁️Serverless：小團隊不需要變成 DBA 團隊

不用處理 instance 規格、vCPU、IOPS、connection pool、WAL backup、index bloat、vacuum、failover、patching。BigQuery 的 serverless 架構讓我們把更多時間放在產品邏輯和 AI 洞察上。

🗂️Columnar Storage：長文查詢的底層優勢

Pandora 查詢通常只需要部分欄位。BigQuery 以 Capacitor columnar format 儲存資料，不用每次把整列都讀出來。對大量長文資料，這不只是快一點，而是整個查詢方式都變得可行。

🧭VECTOR_SEARCH：不用額外維護向量資料庫

不用多維護 Milvus、Pinecone、或 pgvector。向量資料和文章 metadata 留在同一個資料平台，減少多系統之間搬資料、同步資料、比對 ID 的成本。

🤖AI.GENERATE_EMBEDDING：資料庫開始是 AI 工作流的一部分

過去 embedding pipeline 要 BigQuery 拉資料 → 應用層呼叫 embedding model → 寫回資料庫 → 再做向量搜尋。未來更多資料處理可以在 BigQuery 裡完成，AI 工作流更靠近資料本身。

⚡Continuous Queries：戰情室越來越即時

BigQuery continuous queries 可以分析 BigQuery 內新進資料，並把結果寫回 BigQuery table 或輸出到 Pub/Sub、Bigtable、Spanner。未來 Pandora 可以把它用在負面聲量異常偵測、特定議題升溫監控、競品突發事件追蹤、每小時熱門討論更新。

選型比較

BigQuery vs PostgreSQL：Pandora 的實際取捨

評估項目 PostgreSQL BigQuery Pandora 最後選擇
OLTP 交易 很強 不適合 PG 勝
千萬筆長文分析 壓力大 適合 BQ 勝
LLM 動態 SQL 需要大量索引規劃 ad-hoc 查詢友善 BQ 勝
向量搜尋 pgvector + 自管索引 原生 VECTOR_SEARCH BQ 勝
Hybrid Search 跨索引系統整合 同一資料平台內處理 BQ 勝
運維負擔 需要 DBA 思維 Serverless BQ 勝
成本模型 instance 常駐成本 按查詢量 BQ 勝
小團隊友善度 中 高 BQ 勝

結論很明確：如果要做的是交易系統，PostgreSQL 很好。如果要做的是 AI Agent 驅動的大規模社群資料分析，BigQuery 更適合。 Pandora 的核心不是 milliseconds 級的 OLTP，而是 10–20 秒內從上千萬筆長文裡面找出可用洞察。這是完全不同的資料庫選型邏輯。

核心價值

Pandora 從 BigQuery 得到的最大價值

BigQuery 幫我們解決了幾個很現實的問題：

✓

不用預測使用者會問什麼。因為 BigQuery 可以承受 ad-hoc 查詢。

✓

不用額外維護向量資料庫。因為 BigQuery 原生支援 vector search。

✓

不用把資料拆到三四個系統。因為全文、向量、metadata、聚合都能放在同一個資料平台。

✓

不用為了社群長文資料養一個 DBA 團隊。因為 BigQuery 的 serverless 架構已經把很多底層維運吃掉。

我們可以把更多時間花在真正重要的地方：

🗣️讓 AI 更懂社群語言
🚨讓品牌更早看見風險
✍️把消費者痛點變成內容策略
📈把競品弱點變成市場機會
結語

AI 時代，資料庫選型就是產品戰略

以前選資料庫，很多時候是工程決策。現在做 AI 產品，資料庫選型已經是產品戰略的一部分。因為 AI Agent 能不能真的有用，取決於它背後能不能穩定查到資料、理解資料、組合資料，最後把資料變成決策。

BigQuery 讓 Pandora 用一個資料平台完成原本需要多套基礎設施才能完成的事。Text-to-SQL、全文搜尋、向量搜尋、RRF Hybrid Search、聲量聚合、情緒分析、戰情室監控、AI Agent 查詢——這些能力放在一起，才讓 Pandora 不只是輿情監測工具，而是品牌在 AI 時代的社群資料決策引擎。

未來的行銷科技，不會只比誰的報表比較漂亮。真正的差異會來自：誰能把市場上混亂的聲音，整理成 AI 可以理解、品牌可以行動的資料資產。

這也是我們選擇 BigQuery 的原因。
